# 胡牌追踪器设计文档

## 1. 范围

胡牌追踪器是一个单机原生 Android 麻将记分工具。首版聚焦手动记分、自动圈庄显示、牌局结算、历史保存、导入导出。不包含拍照识别、云端服务、用户登录和联网同步。

## 2. 目标

- 快速创建一局麻将记分。
- 支持 2~4 名玩家。
- 支持等额记分和非等额记分。
- 自动显示并推进当前圈和庄。
- 提供总积分、胡牌次数、平均得分和结算差额。
- 本地保存数据，并支持导入导出。
- 结算前允许修改记录，结算后锁定。

## 3. 默认假设

- 首版支持 2~4 人。玩家按输入顺序分配东、南、西、北座位。
- 等额模式输入的分数表示每个输家扣除的单人分，但界面只记录正分。
- 非等额模式要求所有玩家分数总和为 0，正分即表示胡牌，不需要额外指定胡牌人。
- 圈庄按记录笔数固定推进，不处理连庄、流局、庄家胡牌等变体。
- 导入导出使用 JSON。CSV 作为当前牌局明细分享格式。
- Android 技术栈为 Kotlin、Jetpack Compose、Room、ViewModel、Kotlin Coroutines。

## 4. 信息架构

应用包含五个主要界面：

- 牌局列表：展示历史牌局、最近牌局状态、新建牌局入口、导入入口。
- 新建牌局：输入玩家名称，选择等额记分模式。
- 记分页：展示当前圈庄、玩家积分、记一笔入口、记录列表。
- 记一笔页或弹窗：按模式录入本次得分，并校验合法性。
- 记录编辑页或弹窗：允许在结算前修改任意未锁定记录。
- 结算页：展示积分统计、胡牌次数、平均得分、差额结算、导出入口。

## 5. 核心流程

### 5.1 新建牌局

1. 用户点击新建牌局。
2. 输入 2~4 个玩家名称或代号。
3. 选择是否等额记分，默认开启。
4. 创建牌局，进入记分页。

### 5.2 等额记一笔

1. 用户在记分页点击记一笔。
2. 选择得分人。
3. 输入单人扣分分数。
4. 系统只保存一条正分记录。
5. 结算时再根据等额规则反推出其余玩家的负分和差额。
6. 保存记录，并推进圈庄。

### 5.3 非等额记一笔

1. 用户在记分页点击记一笔。
2. 为每个玩家输入本笔分数。
3. 系统校验所有分数总和为 0。
4. 所有正分自动视为胡牌。
5. 保存记录，并推进圈庄。

### 5.4 修改记录

1. 用户在记分页点击某条记录。
2. 如果牌局尚未结算，进入记录编辑页或弹窗。
3. 编辑内容沿用记一笔时的模式和校验规则。
4. 保存后系统重新计算统计结果，并按记录顺序重算后续圈庄。
5. 如果牌局已经结算，记录只读，不允许修改。

### 5.5 查看结算

1. 用户进入结算页查看结算预览。
2. 系统按记录汇总每个玩家的总积分。
3. 统计每个玩家的胡牌次数，口径为正分记录次数。
4. 计算每个玩家平均每次得分。
5. 在等额模式和非等额模式下均可生成付款明细。
6. 用户确认结算后，系统将牌局标记为已结算，锁定所有记录。

## 6. 数据模型

### Game

- `id`: 牌局 ID。
- `createdAt`: 创建时间。
- `updatedAt`: 更新时间。
- `scoringMode`: `EQUAL` 或 `MANUAL`。
- `status`: `ACTIVE` 或 `FINISHED`。
- `currentRoundIndex`: 当前圈索引，0 到 3 分别表示东南西北。
- `currentDealerIndex`: 当前庄家索引，对应玩家列表位置。

### Player

- `id`: 玩家 ID。
- `gameId`: 所属牌局 ID。
- `name`: 名称或代号。
- `seatIndex`: 座位索引，0 到 3 分别表示东南西北。

### ScoreEntry

- `id`: 记录 ID。
- `gameId`: 所属牌局 ID。
- `createdAt`: 记录时间。
- `roundIndex`: 记录发生时的圈。
- `dealerPlayerId`: 记录发生时的庄家。
- `note`: 备注。

### ScoreDelta

- `entryId`: 所属记录 ID。
- `playerId`: 玩家 ID。
- `delta`: 本笔分数。等额模式只保存正分；非等额模式保存每个玩家的正分、负分或 0。
- `isWin`: 是否计入胡牌次数。

## 7. 计算规则

### 7.1 当前圈庄

- 新牌局从东风圈、第一位玩家为庄开始。
- 每保存一笔记录后庄家推进到下一位玩家。
- 庄家从最后一位玩家回到第一位玩家后，圈推进一位。
- 圈按东、南、西、北循环。
- 由于人数可能少于 4，完整循环长度为 `playerCount * 4`，不是固定 16 笔。

如果最终确认必须严格 16 笔一循环，则需要把庄位和实际玩家分开建模。

### 7.2 总积分

- 等额模式：对每个玩家累加自己所有正分，得到“得分合计”。此时不记录也不展示逐笔负分。
- 非等额模式：对每个玩家累加所有 `ScoreDelta.delta`，得到“积分净额”。

### 7.3 胡牌次数

对每个玩家统计正分记录出现次数。

### 7.4 平均每次得分

`平均每次得分 = 总积分 / 胡牌次数`。胡牌次数为 0 时显示为 0 或 `-`，避免除零。

### 7.5 差额结算

等额模式按最终得分合计做两两差额：

1. 比较任意两个玩家的得分合计。
2. 分少的一方给分多的一方支付差额。
3. 汇总每个玩家的应收应付，得到结算净额。
4. 输出付款明细，例如“张三 给 李四 20 分”。

非等额模式可以直接按积分净额生成付款明细：

1. 将积分净额大于 0 的玩家作为收款方。
2. 将积分净额小于 0 的玩家作为付款方。
3. 按绝对金额从大到小匹配，直到双方余额清零。

## 8. 本地存储

使用 Room 保存结构化数据。数据访问通过 Repository 封装，ViewModel 不直接依赖 Room DAO。

建议表：

- `games`
- `players`
- `score_entries`
- `score_deltas`

导入导出使用单个 JSON 文件，结构包含版本号、牌局、玩家、记录和分数明细。导入时按版本号解析，未来可做迁移。

## 9. UI 状态与校验

- 玩家名称不能为空，去掉首尾空格后保存。
- 同一局内玩家名称建议不重复；如果重复，需要二次确认或自动附加座位区分。
- 等额模式分数必须为正整数。
- 非等额模式允许正数、负数和 0，但总和必须为 0。
- 记录可在结算前修改，结算后只读。
- 删除记录需要确认，删除后重新计算后续圈庄。
- 导入数据前校验 JSON 版本、字段完整性和分数总和。

## 10. 项目结构建议

```text
app/
  src/main/java/.../hutracker/
    data/
      db/
      model/
      repository/
    domain/
      scoring/
      settlement/
      round/
    ui/
      gameList/
      newGame/
      scoring/
      settlement/
      importExport/
```

核心计算放在 `domain` 层，使用普通 Kotlin 类实现，便于单元测试。Compose 页面只负责展示和触发意图。

## 11. 测试策略

- 单元测试覆盖记录编辑后的重算、等额记分、非等额记分校验、圈庄推进、总积分统计、胡牌次数、平均得分、差额结算。
- Room 可用 instrumentation test 覆盖基本增删查。
- UI 测试覆盖新建牌局、记一笔、查看结算的主路径。

## 12. 风险

- 圈庄规则和真实麻将规则不完全一致，后续如果要支持连庄或流局，需要重构推进逻辑。
- 等额模式只记录正分，导出和结算展示需要明确区分“得分合计”和“结算净额”。
- 2 人或 3 人模式下，传统东南西北语义会变弱，界面应优先显示玩家名和当前庄家，方位作为辅助信息。
- 导入导出如果后续需要跨版本兼容，首版 JSON 必须带版本号。
