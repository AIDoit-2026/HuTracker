# 胡牌追踪器-一款麻将自动算番记分工具

## 目标
打造一款通过拍照识别国标麻将番数，并记录分数的小工具。分为客户端和服务端两个项目。服务端用nodejs开发，客户端拍照，然后发送到服务端调用roboflow的api识别出牌面，再通过算法计算出番数。

> 需要确定的问题
1. 客户端形式是手机软件，用Android原生还是react native?
2. 计算番数放在客户端还是服务端？

## 客户端功能描述
使用场景是线下打麻将，然后有人拍照进行番数计算，并且记分。
操作流程：
有人胡牌后，就把14张牌拍进去提交云端进行识别，然后根据国标番型计算出所有番数。
细节问题
1. 拍照，胡牌的那手牌肯定必须拍进去，是否需要拍照人不要拍到桌面上其他的正面牌？
2. 麻将玩法中有吃、碰、杠、吃胡这些信息是需要手动标注的，吃和吃胡还涉及到吃的是哪一张牌，结果是有所不同的， 怎么操作比较好？
3. 每次玩都是固定人数的3人或者4人，可以预先输入对局人，后续指定每局谁得分就行。
4. 记分选项可配置，底分多少，是否允许放炮。允许放炮的话，只有胡牌的人得分，放炮的人丢分，其余两人分数不变。
5. 记录圈数和局数，麻将分为东南西北四个圈，每个圈内又分为东南西北四局。

## 问题分析（AI）

### 1. 客户端用 Android 原生还是 React Native？

分析：
当前产品的核心客户端能力是拍照、上传图片、展示识别结果、人工修正牌面/副露信息、记录分数。第一版如果只面向 Android 手机使用，Android 原生实现成本更低、相机能力和本地权限控制更直接，稳定性也更好。React Native 的优势主要在于后续同时支持 iOS，但会引入跨端框架、原生相机插件、打包调试和权限适配等额外复杂度。

推荐结论：
第一版建议使用 Android 原生。先把拍照识别、番型确认、记分流程跑通。等规则、交互和用户习惯稳定后，如果确实需要 iOS，再评估是否扩展为跨端方案。

### 2. 番数计算放在客户端还是服务端？

分析：
番数计算依赖国标麻将规则、识别结果修正、吃碰杠/和牌方式等上下文。放在服务端可以让规则版本统一，后续修正规则或增加番型时不需要强制更新客户端，也方便记录识别输入、计算过程和异常案例。客户端只负责采集、确认和展示，职责更清晰。缺点是离线不可用，但当前识别本身已经依赖云端 API，所以第一版没有必要为了离线计算增加复杂度。

推荐结论：
番数计算建议放在服务端。客户端提交图片和人工补充信息，服务端完成牌面识别、规则计算和结果返回。客户端可保留简单的结果展示和本地缓存，不承担核心番型逻辑。

### 3. 拍照时是否要避免拍到桌面上其他正面牌？

分析：
识别模型如果同时看到胡牌手牌之外的正面牌，容易把无关牌误识别进结果，导致需要更多人工修正。第一版为了降低识别和算法复杂度，应把输入范围限定清楚：照片只包含胡牌人的 14 张牌，以及必要时单独录入的副露牌。不要依赖模型自动判断哪些牌属于本次胡牌，哪些是桌面上的无关牌。

推荐结论：
第一版要求拍照时尽量只拍胡牌人的牌，不拍桌面其他正面牌。客户端可以提供拍照取景框/裁剪框，让用户把 14 张牌放入指定区域；识别后必须提供牌面确认和手动修正入口。

### 4. 吃、碰、杠、吃胡等信息怎么操作比较好？

分析：
吃、碰、杠、明杠、暗杠、补杠、自摸、点炮、吃胡来源牌等信息，仅靠最终照片很难稳定判断，而且这些信息会影响番型和记分结果。让用户在拍照前完整录入会打断线下打牌节奏；让用户在识别后补充，操作负担更小，也能基于识别出的牌面做结构化选择。

推荐结论：
采用“拍照识别 + 结果确认 + 结构化补充”的流程。识别后先展示 14 张牌结果，用户确认或修正牌面；然后在同一页选择和牌方式：自摸/点炮，若点炮则选择放炮人；再补充副露信息：吃、碰、杠分别作为一组牌录入，吃需要标记被吃的是哪一张，杠需要区分明杠/暗杠/补杠。最终把牌面、副露、和牌方式、胡牌人、放炮人、底分、是否允许放炮等信息一起提交服务端计算。

### 综合建议

第一版产品应优先保证主流程可靠：Android 原生客户端拍照上传，服务端调用识别并计算番数，客户端负责人工确认和记分展示。识别模型只解决“看清牌面”的问题，不把复杂玩法上下文交给图片识别推断；吃碰杠、和牌方式、玩家、底分、放炮规则、圈数局数都作为结构化数据录入。这样实现边界清楚，后续无论优化识别模型、扩展番型规则，还是增加 iOS 客户端，都比较容易演进。
